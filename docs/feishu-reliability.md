# OpenCode 飞书通道可靠性记录

> 更新日期：2026-07-22  
> 适用组件：`opencode-lark` + 飞书 WebSocket 事件订阅 + OpenCode Server

本文记录当前飞书桥接的消息重放问题、已确认根因和建议修复方案。安装与日常使用仍参考 [OpenCode + 飞书通道](../agents/opencode/feishu/README.md)。

## 结论摘要

当前飞书通道可以使用，但存在一个影响无人值守任务的可靠性风险：同一条用户消息可能在首次处理后的数十秒、数小时再次送达，并被重复提交给 OpenCode。

本地启动脚本可以解决工作目录、端口、进程归属和 TUI 会话绑定问题，但无法从外部彻底修复消息 ACK 与业务幂等性。根治需要修改 `opencode-lark` 的事件处理路径。

在上游修复前，不建议让飞书通道无人值守执行具有不可逆副作用的操作，例如发布、推送、删除资源或修改生产环境。

## 已观察现象

同一个飞书事件曾在以下时间尺度重复出现：

- 首次处理后约 20 秒。
- 首次处理后约 1 小时。
- 首次处理后约 6 小时。

重复消息具有相同的飞书 `message_id`，业务内容也相同，因此不是用户重复发送或 OpenCode 自己重试。重放时间可能超过当前桥接的去重窗口。

## 根因分析

问题由两个条件叠加形成。

### 1. WebSocket ACK 被业务处理阻塞

`opencode-lark` 的 WebSocket 消息处理会等待完整的 `onMessage` 业务流程完成。该流程可能继续等待 OpenCode 执行和回复，因此飞书侧不能及时收到事件 ACK。

当 Agent 任务耗时较长、网络短暂中断或进程重连时，飞书平台可能把未确认事件重新投递。

### 2. 去重窗口不足且键选择不完整

当前实现按 `event_id` 做持久化去重，但 TTL 只有 60 秒。它存在两个问题：

- 数小时后的平台重放已经越过去重窗口。
- 消息级副作用更适合使用稳定的 `message_id` 作为业务幂等键；仅依赖事件投递层的 `event_id` 不够稳健。

因此，即使短时间重放被挡住，延迟重放仍可能再次向 OpenCode 提交相同 Prompt。

## 为什么启动脚本不能根治

`start-opencode-remote.ps1` 负责以下本地生命周期问题：

- 只复用工作目录一致的 OpenCode Server。
- 自动选择空闲端口并识别进程归属。
- 清理旧 bridge 和本脚本启动的进程。
- 从 bridge 日志中定位准确的 session 并启动 TUI attach。

消息是否被快速 ACK、是否已处理过，则由 bridge 内部决定。启动脚本看不到完整事件载荷，也无法在提交 OpenCode 前建立可靠的原子幂等检查。

## 建议修复方案

### P0：接收与处理解耦

WebSocket 收到事件后应快速完成协议 ACK，再把事件放入有界队列或后台 worker。ACK 不应等待 OpenCode 完成 Prompt。

需要同时满足：

- ACK 路径不等待模型响应。
- 同一 chat 内保持消息顺序。
- worker 异常可观察，并有明确的失败处理策略。
- 队列必须有容量限制，避免故障期间无限占用内存。

### P0：持久化业务幂等

在产生 OpenCode 副作用之前执行原子去重：

1. 优先以飞书 `message_id` 作为消息幂等键。
2. `event_id` 可作为投递事件的辅助键。
3. 使用 SQLite 唯一约束或事务完成“检查并占位”，避免并发竞态。
4. 去重记录至少保留 24 小时，建议 7 天，并通过定期清理控制体积。
5. 重启 bridge 后仍能识别已经处理的消息。

建议将状态区分为 `processing`、`completed` 和 `failed`。对于 `failed` 是否允许重试，需要按副作用语义显式决定，不能简单删除记录后自动重放。

### P1：可观测性

日志至少记录以下字段：

- `event_id`
- `message_id`
- `chat_id`
- 首次接收时间
- 当前投递是否被判定为重复
- ACK 延迟
- 业务处理耗时和最终状态

日志中不应输出 App Secret、访问令牌或完整敏感消息正文。

## 验收条件

上游修复应覆盖以下自动化测试：

1. `onMessage` 阻塞数分钟时，协议 ACK 仍在平台要求的时间内完成。
2. 相同 `message_id` 在 20 秒、1 小时、6 小时后重放，只产生一次 OpenCode Prompt。
3. bridge 重启后重放相同消息，仍不会重复执行。
4. 两个不同消息即使文本完全相同，也都能正常处理。
5. 同一 chat 的多条消息保持顺序，不同 chat 不必互相阻塞。
6. 去重数据库暂时不可用时采取保守策略并产生清晰告警。

## 当前处置建议

### 继续使用飞书时

- 把任务设计为可重复执行，尤其是脚本、数据库迁移和发布命令。
- 对 `git push`、部署、删除等高风险操作保留人工确认。
- 发现旧命令再次出现时，先中止 Agent，再检查 bridge 日志中的 `message_id`。
- 保留 bridge 数据目录，避免重启时丢失持久化状态。

### 迁移选择

如果首要目标是国内网络直连，继续飞书并推动上游修复仍有价值。如果首要目标是成熟的移动交互、项目切换和 supervisor 能力，可并行验证 Telegram 方案，详见 [OpenCode Telegram Bot 调研](telegram-bot-research.md)。
